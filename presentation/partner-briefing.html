What we built

A SaaS product — not a feature,
not a service. A scalable product
you own and can sell.

What it is

A candidate identity and fraud verification platform for staffing, HR, and hiring teams. Proves the person you interview is the real, government-ID-verified person — at submission, interview, and offer stage. Built on top of enterprise-grade biometric infrastructure.

What it is NOT (v1)

Not a traditional background check. No employment history, criminal records, education verification. Those need country-specific data sources and manual ops. We stay on the identity/anti-deepfake slice — that is where the pain is hottest and where incumbents are weakest.

Why this specifically

Gartner projects 1 in 4 candidate profiles will be fake by 2028. IT and tech roles account for ~60% of deepfake fraud — exactly the talent this channel places. The window to be first with a real product is now.

The advantage

An existing sales channel with 70+ active clients across staffing, RPO, Web3, and IT hiring. The product goes to market through relationships that already exist. No cold outreach needed to run pilots.

The infrastructure layer — Didit

Didit is the biometric engine.
TrueHire is the product
built on top of it.

What Didit provides

  • ✓Government ID OCR (220+ countries, 10,000+ document types)
  • ✓Liveness detection (iBeta PAD Level 1 — deepfake-resistant)
  • ✓Face match 1:1 (compare two images)
  • ✓Face search 1:N (search entire pool)
  • ✓AML / PEP / sanctions screening
  • ✓IP analysis (VPN, proxy, Tor)

How we use it

  • →Create verification sessions server-side — never expose the API key to the browser
  • →Send candidates a hosted URL — Didit handles biometric consent + camera
  • →Receive results via signed webhook (HMAC-SHA256)
  • →Store decisions, run face-match for C2/C3

Why Didit (not build-your-own)

  • ★iBeta PAD L1 certification — courts and regulators accept it
  • ★500 free verifications/month — zero pilot cost
  • ★Per-call pricing — cost scales with revenue
  • ★Bank-grade compliance built in

Didit — API calls we make

Six API calls.
The full verification chain.

Call Endpoint When What it does Checkpoint
POST Create session /v3/session/ Recruiter triggers check Creates hosted verification URL for candidate C1 C2 C3
GET Get decision /v3/session/{id}/decision/ On webhook or on-demand Fetches full verification result JSON C1 C2 C3
POST Face match /v3/face-match/ After C2/C3 approved 1:1 compare new selfie vs C1 reference image → MATCH or NO MATCH score C2 C3
POST Face search /v3/face-search/ After C1/C2/C3 approved 1:N search across entire pool — detects one person with multiple fake identities C1 C2 C3
POST Generate PDF /v3/session/{id}/pdf On recruiter request Returns compliance-grade PDF report for download C1

Webhook: Didit sends status.updated and data.updated events to /api/webhooks/didit — HMAC-SHA256 signed, timestamp-checked, idempotent. All C2/C3 post-processing (face-match, pool search) happens automatically on this webhook.

Technology stack

Full-stack web app.
Modern, scalable, live.

Frontend + Backend

Next.js (App Router) on Vercel. Server components for pages, route handlers for API. TypeScript throughout. Tailwind CSS. Auto-deploy on every GitHub push.

Database + Auth

Supabase (Postgres + Auth). Row-level security so recruiters see only their own candidates. Admin, recruiter, and client-viewer roles. Cookie-based sessions via @supabase/ssr.

Verification Engine

Didit API. Server-side session creation only — API key never reaches the browser. Webhook handler with HMAC signature verification, replay protection, and idempotency.

Data stored per candidate

candidates (identity record) → verifications (one row per C1/C2/C3) → decision_json, face_match_score, liveness_score, duplicate_face_flag → webhook_events (dedupe), audit_log

11 / 15
The sales conversation

Five questions.
Ask these first. Then show the product.

Q1 — Has it happened?

"In the last year, have you been burned by a candidate who wasn't who they claimed — a proxy, a fake profile?"

Good signal: a specific story. No signal: "not really" — wrong buyer, move on.

Q2 — What do they do now?

"Walk me through how you verify a candidate is real today."

Listen for: manual effort, "we check LinkedIn," no process at all. The worse their answer, the bigger your opening.

Q3 — What does a miss cost?

"What happens if a fraudulent hire gets through to your client?"

Listen for: lost client, compliance incident, security breach. The bigger the stated cost, the higher they'll pay.

Q4 ★ THE MONEY QUESTION

"If there was a 2-minute check that guaranteed the interviewee is real — what would it be worth per candidate? Would you pilot 50 hires?"

A number = buyer. "Interesting" = not ready.

Q5 — Path to yes

"Who signs off on this, and how does it need to fit into your hiring process?"

Listen for: the actual decision-maker and ATS integration constraints. Shapes what we build next.

Common objections — pre-answered

Every objection you'll hear.
The exact response.

"We already do background checks."

BGV tells you who someone was — not whether the person on your video call is that person today. It doesn't run at the interview stage. It doesn't detect deepfakes or proxies. TrueHire is the layer that incumbent BGV providers simply don't have.

"Candidates won't agree to this."

2 minutes on their phone, no app, no account. Faster and less invasive than a police verification. For a competitive role, candidates who are genuine want to prove it — it's a differentiator for them.

"Too expensive / complicated to set up."

The recruiter sends a link. That's the setup. First 500 verifications are free. Per-candidate pricing — no contract, no minimum. A login and you're live in minutes.

"What about DPDP / data privacy?"

Explicit consent before the check starts. Didit is enterprise-grade infrastructure. Better for compliance than a manual process with no audit trail. Data minimisation built in.
